## Context

The repository has a working build, a green CI gate and a deployed shell that
renders nothing. `vendor/runewizard/` holds a verified, read-only snapshot of
the upstream MIT-licensed data. This change turns that snapshot into a dataset
`src/` may import. See [`proposal.md`](proposal.md) for why it comes first.

Five facts about the current state shape the design. All five were verified
against the vendored files rather than assumed:

- **The vendor data is complete and internally consistent.** 99 runewords, 99
  description blocks keyed by title with no key mismatched in either direction,
  33 runes in 11/11/11 tier bands, 20 item categories of which every one is
  actually referenced, 343 rune slots, socket counts from 2 to 6, 9 ladder-only
  entries, 1 note, patches `1.10`/`1.11`/`2.4`/`2.6`/`3.0` on 74 of 99. Five
  runewords repeat a rune — `Sanctuary`, `Infinity`, `Last Wish`, `Phoenix`,
  `Bone`. Every `tinfos` value is parenthesis-wrapped.
- **The vendor files cannot be statically imported.** `runewords.ts` annotates
  with `TRuneword`, `item-types.ts` with `TItemTypeId`,
  `runewords-descriptions.ts` with `TRunewordMeta` — none of which any of those
  files declares. A static `import` would also drag `vendor/` into
  `pnpm typecheck`, which the `build-toolchain` spec forbids. `runes.ts`
  additionally declares an `export const enum`, so Node's type-stripping loader
  cannot read it either.
- **The property blocks are template literals, not clean lines.** Across the 99
  blocks there are 201 blank lines and 974 indented lines. Splitting needs
  trimming and blank-dropping, and the results range from 4 property lines
  (`Wealth`) to 26 (`Fortitude`).
- **Prettier owns the formatting of every committed file**, JSON included, via
  `lint-staged` and `format:check`. A generator that writes JSON is writing a
  file Prettier will then have an opinion about.
- **The dataset has no visible surface.** Nothing renders it, so "it works"
  cannot be judged by loading the page. The tests are the acceptance evidence.

## Goals / Non-Goals

**Goals:**

- One dataset, in our own field names, that every later Phase 1 feature reads
  without transforming it further.
- No hand-transcribed game data anywhere in the repository.
- The committed data and its generator cannot silently diverge.
- Malformed data fails loudly and early — in CI, not in a player's browser.
- Cross-references hold: every rune name resolves, every item category resolves.
- Zero new dependencies.
- The MIT attribution travels with the derived data.

**Non-Goals:**

- Any rendering, any styling, any rune sprite.
- Classifying categories into filter slots, or any other interpretation of the
  data. This change transforms; it does not judge.
- Crafted state, persistence, or the remaining-runes and remaining-bases
  aggregation.
- Translations, and any structural parsing of property lines to support them.
- Correcting the vendor data's game accuracy.
- A runtime data-refresh mechanism. The dataset is a build-time artifact.

## Decisions

### The dataset is generated by a committed script, not transcribed

`scripts/generate-dataset.ts` reads `vendor/`, validates, transforms and writes
`src/data/*.json`, exposed as `pnpm data:build`.

This is the load-bearing decision of the change. A transcription error in game
data is invisible in a way almost no other bug is: a required level of 62 where
the game says 65 type-checks, lints, renders and reads perfectly, and fails only
when a player farms the wrong runes. Tests cannot catch it because there is
nothing to compare against except the source we would have been copying from.
Generating removes the entire error class instead of trying to detect it.

It also makes a vendor refresh cheap. When a patch adds runewords, the work is
re-cloning the snapshot and re-running one command, rather than diffing 45 KB of
game data by eye.

_Alternative considered:_ transform once by hand and delete the generator,
keeping only the invariant tests. Rejected — the invariant tests verify
structure, not values, so they would pass over a dataset with a wrong level in
it. The generator is what makes the values trustworthy, and it costs about as
much to keep as to throw away.

### Vendor files are loaded as text, transpiled in memory, and evaluated

The generator reads each vendor file with `readFileSync`, strips its types with
`typescript`'s `transpileModule` to CommonJS, and evaluates the result through
`new Function("exports", "require", js)` with a `require` that throws.

This was chosen against three alternatives and then verified end to end — all
four vendor files load, including `runes.ts` with its `const enum`, and every
count matches what `docs/DATA-SOURCES.md` records.

- _Static `import` of the vendor `.ts` files._ Rejected: the files reference
  types they do not declare, and importing them from a type-checked path pulls
  `vendor/` into `pnpm typecheck`, which the `build-toolchain` spec forbids.
- _Regex extraction from the file text._ Rejected for `runewords.ts` — nested
  arrays, five optional fields and interleaved comments make a regex a slow
  correctness bug waiting to happen. Acceptable for `runes.ts` alone, but that
  would mean two techniques where one now suffices.
- _Node's `--experimental-transform-types` so `runes.ts` imports directly._
  Rejected: it makes the generator's correctness depend on an experimental
  loader's handling of `const enum`, to save code that is already written.

`typescript` is already a devDependency, so the technique adds nothing to the
manifest. Evaluating vendor code is build-time only and never reaches the
bundle; the files are committed, reviewed and read-only, and the injected
`require` throws so an evaluated module cannot reach outside itself.

### `zod` validates both ends of the transformation, not just the output

Two schema sets: one describing the **vendor** shape, parsed immediately after
evaluation, and one describing **our** shape, parsed before the JSON is written
and again when the app loads it.

Validating the input is the half that is easy to skip and the half that pays.
The vendor snapshot is the one input to this system that can change without us
changing anything — a refresh that renames `ttypes` or turns `level` into a
string would otherwise produce plausible-looking JSON full of `undefined`.
Parsing at the boundary turns that into a named error on the field that moved.
This is also the concrete reading of `AGENTS.md`'s "validate the dataset with
`zod` rather than trusting its shape".

The vendor schema is strict about what it knows: exactly the eight observed keys
(`title`, `runes`, `level`, `ttypes`, `tinfos`, `version`, `ladder`, `note`), so
a new upstream field is a visible failure rather than silently dropped data.

### The `zod` schemas are the source of truth for the types

`src/data/schema.ts` declares the schemas; the TypeScript types are
`z.infer<typeof …>`. There is no hand-written `interface` describing the same
shape.

One declaration, so the validator and the compiler cannot disagree. Declaring
both is the standard way to end up with a type that permits what the schema
rejects.

### Validation runs at module load, unconditionally

`src/data/index.ts` imports the three JSON files, parses each at module
initialisation, and exports the validated results.

The tempting optimisation is to validate only in tests, since CI already proves
the committed JSON is valid and re-parsing a constant at runtime looks like
waste. Rejected, for a reason specific to how this file will be maintained:
`src/data/runewords.json` is a plain JSON file in a repository, and the likely
future edit is somebody fixing one property by hand rather than re-running the
generator. Load-time parsing is what makes that edit fail loudly. It costs
roughly a millisecond for 99 records, and `zod` is already a runtime dependency
declared for exactly this purpose.

_Consequence accepted:_ invalid data means a blank page rather than a degraded
one. That is the correct failure for a tracker whose entire content is the
dataset — a partially rendered table of unvalidated game data is worse than an
obvious failure — and the drift test plus CI are what keep it from ever shipping.

### Three JSON files, one entry point

`src/data/runewords.json`, `runes.json`, `item-types.json`, all re-exported
through `src/data/index.ts` (`@/data`).

Three files because they have three shapes, three schemas and three lifetimes —
the rune list has not changed since 2003, while runewords change per patch.
Splitting keeps a patch diff to the file that actually changed. One entry point
because consumers should never import a raw JSON file and skip validation.

The entry point also exports `Map` lookups by name for runes and item types.
Every consumer needs them — the table resolves 343 rune references — and
building them once at load beats a linear scan per cell.

It does **not** export a `socketCount()` helper. The count is `runes.length`; a
function wrapping one property access adds indirection and, worse, invites
someone to cache the result in a field, which is the drift `AGENTS.md` forbids.

### Property lines are merged into the runeword record

`properties: string[]` lives on the runeword, split from the vendor template
literal on newlines, trimmed, with empties dropped. The description file does
not survive as a separate artifact.

The key-matching problem is solved once, at generation time, where a mismatch is
a build failure — instead of every runtime consumer having to handle a missing
key. Verified: the two vendor files agree on all 99 keys in both directions
today, and the generator asserts it rather than assuming it holds after a
refresh.

A flat array of English lines is deliberately the least structured thing that
works. Parsing `+50% Enhanced Defense` into a value and a stat would be
speculative until Phase 2 states what the Russian client actually needs, and a
wrong structure is harder to undo than an absent one.

### Field-by-field normalisation, with the reasoning where it is not obvious

| Vendor           | Ours                  | Note                                 |
| ---------------- | --------------------- | ------------------------------------ |
| `title`          | `name`                | unique; the canonical identifier     |
| `runes`          | `runes`               | order significant, repeats preserved |
| `level`          | `requiredLevel`       | 13–69                                |
| `ttypes`         | `itemTypes`           | each resolves to `item-types.json`   |
| `tinfos`         | `itemTypeRestriction` | parentheses stripped                 |
| `version`        | `patch`               | omitted on the 25 pre-1.10 runewords |
| `ladder`         | `ladderOnly`          | normalised to a boolean on all 99    |
| `note`           | `note`                | omitted unless present               |
| _(descriptions)_ | `properties`          | merged in, one entry per line        |
| _(none)_         | —                     | socket count stays derived           |

Two of those are judgement calls worth stating:

**Parentheses are stripped from the restriction.** The stored value is
`Assassin`, not `(Assassin)`. Punctuation is presentation, and Phase 2 has to
translate the word without the brackets getting in the way. The generator
asserts every source value is bracket-wrapped before stripping, so the rule
cannot quietly mangle a value that does not fit it.

**`ladderOnly` is present on all 99 as a real boolean**, unlike the other three
optional fields. Consumers read a boolean rather than testing for a key, which
is worth 90 extra short lines in a generated file. `patch`, `note` and
`itemTypeRestriction` stay absent when they do not apply, because none of them
has a meaningful empty value and inventing `""` would just move the check.

### Availability fields carry no logic — enforced by a test, not a comment

`ladderOnly`, `patch` and `note` exist to render badges. `IDEAS.md` settled
this, and the reason is that availability flips between seasons: Mosaic is
flagged ladder-only _and_ noted as disabled in Season 13 and craftable offline
non-ladder. Any rule expressed as code is wrong within a season or two, whereas
a stale badge is a cosmetic inaccuracy.

The spec states it as a requirement and the test suite asserts the progress
denominator is 99 regardless of the flags, so the constraint has a failing test
behind it rather than only a paragraph in a document.

### The generator writes Prettier-formatted JSON, and the drift test compares parsed data

Both halves are needed and they protect different things.

The generator runs its output through Prettier's API with the repository's own
config, so `pnpm data:build` leaves a tree that `format:check` already accepts.
Without it, regenerating always produces a diff — `JSON.stringify(…, null, 2)`
expands `["Ral","Ort","Tal"]` across four lines where Prettier keeps it on one —
and every regeneration would need a `pnpm format` chaser.

The drift test then compares **parsed objects**, not text. That way a formatting
change can never fail the data test, and the data test can never be satisfied by
reformatting. Each check owns exactly one concern.

### The generator runs under plain `node`, with no runner dependency

`"data:build": "node scripts/generate-dataset.ts"`, relying on Node's built-in
type stripping. Verified on the pinned Node 24.9.0.

No `tsx`, no `ts-node`, no `vite-node` — the project's dependency budget is
explicitly tight and this needs none of them. The constraint it accepts is that
the generator's own source must stay erasable-syntax-only: no `enum`, no
`namespace`, no parameter properties. `verbatimModuleSyntax` is already enabled
repo-wide, so the discipline is one the codebase follows anyway, and
`pnpm typecheck` covers the script once `scripts` joins `tsconfig.node.json`.

### The JSON is imported, not fetched

Vite inlines the three files into the bundle. `resolveJsonModule` is already on.

Roughly 45 KB, and in exchange there is no loading state, no error state, no
race between first paint and data arrival, and no fourth network request on a
page whose entire content is this data. For a static site with no backend,
fetching data that is already in the deployment buys nothing.

### Vendor array order is preserved

The 99 records stay in the vendor's patch-grouped chronological order.

Nothing depends on it — the default sort is by required level — but keeping it
makes a diff after a vendor refresh readable, since new runewords append to
their patch group instead of scattering through an alphabetical list.

### Rune tiers become strings

`tier: "common" | "semirare" | "rare"` rather than the vendor's `1 | 2 | 3`.

The panel groups by tier, and `tier === "rare"` cannot be misread the way
`tier === 3` can. The numeric ordering is not lost — the array order already
carries the canonical rune progression, which is a stronger ordering than the
three-band tier anyway.

## Risks / Trade-offs

- **A wrong data value is invisible to every check** → The reason the dataset is
  generated rather than transcribed. Residual risk is an upstream error, which
  is out of scope by design and would need its own evidenced change.
- **Load-time validation failure is a blank page** → Accepted deliberately, as
  argued above. Mitigated by the drift test and the invariant tests running in
  CI, so invalid JSON cannot reach `main`.
- **The generator evaluates vendor code** → Build-time only, never bundled;
  vendor files are committed, reviewed and read-only, and the injected `require`
  throws so the evaluated module cannot reach beyond itself.
- **A vendor refresh may change the upstream shape** → The strict vendor-side
  schema fails on the specific field that moved, rather than emitting a dataset
  full of `undefined`. The refresh procedure itself already lives in
  `docs/DATA-SOURCES.md`.
- **`transpileModule` behaviour could change across TypeScript majors** → It is
  the compiler's own single-file transpile path with no type resolution, the
  most stable thing in the API surface, and the drift test exercises it on every
  CI run, so a regression shows up as a red test rather than as bad data.
- **Node's type stripping is still marked experimental** → It only affects
  `pnpm data:build`, a developer-invoked command. CI never runs the generator;
  it runs the drift test, which goes through Vite's transform instead. So a
  loader regression cannot break the build or the deploy.
- **45 KB of JSON in the bundle** → Accepted for the simplicity it buys. If it
  ever matters, splitting `properties` into a lazily-imported chunk is a
  contained follow-up, since `properties` is only read when a popover opens.
- **This change ships no visible behaviour** → Acceptance is test output and a
  green gate, not a screenshot. Worth stating so the change is not judged by
  loading the deployed site and seeing the same shell as before.
- **The generator is a second way to produce `src/data/`** → Someone can edit
  the JSON directly and skip it. The drift test turns that into a failure that
  names the file, which is the earliest honest signal available; load-time
  validation catches the subset that is also malformed.

## Migration Plan

No runtime migration. Nothing consumes the dataset yet and nothing is persisted,
so the change is purely additive and there is no state to convert.

1. Add the schemas, then the generator, then run `pnpm data:build` and read the
   emitted JSON — spot-check `Infinity` for repeat preservation, `Mosaic` for
   all three availability fields, `Wealth` for the shortest property list and
   `Fortitude` for the longest.
2. Add the invariant tests and the drift test. Confirm the drift test fails when
   a value in the committed JSON is edited by hand, then restore it.
3. Wire the tooling: `tsconfig.node.json` include, the ESLint block for
   `scripts/`, the `data:build` script.
4. Add the `NOTICE` and the README credit.
5. Run the full local gate, then push and confirm CI stays green.

**Rollback:** revert the commit. Nothing outside `src/data/`, `scripts/`, the
four config files and `NOTICE` is touched, no persisted state exists, and no
consumer imports the dataset yet, so a revert is complete by construction.

## Open Questions

None blocking. Three things deliberately left open:

- **Which filter slot `Grimoire` belongs to.** It appears alongside `Shields` on
  `Ancient's Pledge` and is one of the four categories with no wiki URL to
  resolve it. The dataset carries categories verbatim and classifies nothing, so
  this blocks nothing here; the slot-filter change has to settle it against the
  game.
- **Whether `properties` eventually needs structure.** Phase 2 decides, once the
  Russian client's strings are in hand. Splitting a flat array later is
  straightforward; unpicking a wrong structure is not.
- **Whether the rune sprite index should be stored on the rune record.** It is
  the array position today, which is free and correct. If the sprite ever gains
  a row the two would need to stop being the same number — a question for the
  change that actually renders an icon.
